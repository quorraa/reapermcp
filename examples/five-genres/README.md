# Five genres, end to end

A worked example that drives the whole product against a real REAPER host: five
composed melodies in five genres, harmonised, arranged, voiced, mixed and
rendered.

It exists because the acceptance walkthrough proves the tools *work*; this shows
what they **do**. Every chord, bass line and countermelody here was generated by
`qlabs-reaper-music-mcp` from nothing but a melody.

## What is authored, and what the server decides

| Authored here | Decided by the server |
|---|---|
| the five melodies (`melody.py`) | key and mode reading |
| tempo, meter, style profile, loop intent | phrase structure and harmonic grid |
| instrument choice and effect chains | the chord progression |
| drum patterns | bass line, countermelody, voicings |
| mix levels | which candidate scores best, and why |

The drum patterns are authored because the product does not write drums — see
[`KNOWN_LIMITATIONS.md` §10](../../docs/KNOWN_LIMITATIONS.md). The instruments
and effects are authored because it does not choose those either (§4). Both are
deliberate scope boundaries, not gaps this example works around.

## The melodies are composed, not listed

`melody.py` builds each tune from a motif and develops it, rather than spelling
out a note list. That is a deliberate correction: the first version of this
example *did* hand-list the notes, and every song came out with the same plod —
almost every note on the beat, durations of one to four beats, a stepwise wander
with no rests and no shape. Harmonising a dull melody gives you a well-dressed
dull melody, which under-sells the engine this example exists to demonstrate.

Each line now has a three-to-five note motif, developed by sequence, inversion
and fragmentation; phrases in antecedent/consequent pairs that come to rest on
an unresolved degree and then home; a single climax in the third phrase,
approached by leap; and rhythm that sits off the beat and leaves room to
breathe. For the jazz ballad that is 44 notes across 64 beats, most of them off
the beat, against 35 entirely on-beat notes before.

Getting that right took three corrections, all found by measuring what the
server made of the melody rather than by listening. The line must not overlap
itself - a melody is one voice, and a single 0.125-beat overlap collapsed the
analysis to one phrase and one chord slot. It must assert its tonic, or the same
seven notes read as a different mode. And the tonic must be held longer than the
dominant, because duration is what decides between two modes that share every
note. Measured against the melody it replaces:

| melody | key | phrases | chord slots |
|---|---|---|---|
| hand-written | F major 0.646 | 4 | 16 |
| composed, first attempt | G dorian | 1 | 1 |
| composed, corrected | F major 0.578 | 4 | 18 |

The jazz ballad returns eighteen chords and 156 staged notes where the first
attempt returned one chord and six.

## The pipeline

Each stage measures rather than assumes, and each can be run on its own:

| Step | What it does |
|---|---|
| `build_project.py` | drives the MCP: analyse, harmonise, arrange, voice, stage |
| `restructure.py` | splits the kit onto Kick / Snare / Hats / Ride so each can be processed |
| `instruments.py` | builds each voice from Surge parameters (see below) |
| `render_stems.py` | renders every track alone, for measurement |
| `gain_stage.py` | sets each fader from measured loudness, then trims the master |
| `drum_bus.py` | compressor across the kit, threshold derived from the bus |
| `track_limiter.py` | limits lead and harmony transients so the mix can sit louder |
| `crest_report.py` | loudness, peak and crest for every mix |

Run them in that order, and **run `gain_stage.py` once more after the
compressor and the limiter**. Both add makeup gain after the master trim was
set, so the mix comes back slightly hot - that is how neo-soul ended a run with
four clipped samples at -0.0 dBFS. Anything that adds gain has to be followed by
a re-trim.

Two things worth knowing before extending this:

**Instruments are real Surge factory patches**, installed by writing the
plugin's state as a chunk when the plugin is created. `build_project.py` does
this per track from the map in `patches.py`; the patch has to be written in the
same script that creates the plugin, or REAPER's save records its own cached
state instead. Routes that do *not* work, and the two conditions that make this
one work, are in
[`KNOWN_LIMITATIONS.md` §21](../../docs/KNOWN_LIMITATIONS.md#21-driving-a-plugin-from-a-script).

`instruments.py` builds voices from parameters instead, which was the approach
before factory patches could be loaded. It is kept because it is what proved
parameter writes reach the audio, and because it works without any patch
library — but the factory patches sound better and are what the pipeline uses.

**Anything automating a plugin must be verified against rendered audio.** Return
values, parameter read-backs and plugin state read-backs all reported success
here while the audio was unchanged. `loudness.py` and `timbre.py` exist for that:
loudness for level, spectra for timbre — and spectra because the same project
rendered twice differs in ~90% of its samples, so comparing waveforms proves
nothing.

## The five

| Song | Key the server read | Confidence | Phrases | Chord slots |
|---|---|---|---|---|
| Jazz ballad | F major | 0.578 | 4 | 18 |
| Neo-soul | E-flat dorian | 0.657 | 4 | 10 |
| Drum and bass | A aeolian | 0.742 | 4 | 5 |
| Cinematic | D natural minor | 0.600 | 4 | 10 |
| Twelve-bar blues | E blues minor | 0.631 | 4 | 6 |

Every key was inferred, not declared. Note that the server does not force a
major or minor label where the music does not support one: the neo-soul melody
reads as **dorian** and the blues as **blues minor**, and each is answered in
kind — eleventh chords that never resolve for the first, dominant sevenths for
the second. The jazz ballad gets tritone substitution and modal interchange:

    Bbm9 | Eb9 | Fmaj9 | Eb6/9 | Fmaj9 | Bbmaj9 | Eb9 | Fmaj9 | Dm9
    Gm9 | Abmaj9 | Gb9 | Fmaj9 | F9 | Bbmaj9 | Eb6/9 | Fmaj9 | Eb9

## Running it

Requires a running REAPER with the bridge started, the MCP server installed, and
Python with `numpy` and `scipy` **for the sample synthesis only**. The Rust
workspace itself still has zero dependencies; nothing here is part of the
product.

```sh
export QLABS_SONGS_DIR=/where/you/want/the/output     # default: ~/qlabs-songs
python make_samples.py            # synthesise the drum samples
python build_project.py           # melody -> generate -> stage -> dress -> render
python restructure.py             # split the kit onto its own tracks
python instruments.py             # build each voice from Surge parameters
python gain_stage.py              # set every fader from measured loudness
python drum_bus.py                # glue the kit
python track_limiter.py           # tame the lead and harmony transients
python gain_stage.py              # re-trim: the last two stages added gain
python crest_report.py            # loudness, peak and crest for every mix
```

`QLABS_REAPER_EXE` overrides the path to `reaper.exe`.

Each script also takes a song id prefix, so `python build_project.py 03_drum`
rebuilds one song.

## The pieces

| File | What it is |
|---|---|
| `mcp_driver.py` | Speaks MCP JSON-RPC over stdio to the real `serve` binary. One process per run, because snapshot and candidate ids live in its session store. |
| `reaper_exec.py` | Runs a snippet of Lua inside the running REAPER and returns what it printed. Compile-checks with `luac -p` first: a syntax error otherwise becomes a blocking dialog inside REAPER and a timeout out here. |
| `songs.py` | Tempo, meter, profile, loop intent and drum patterns, as data. The melodies come from `melody.py`. |
| `melody.py` | Composes each melody from a motif: sequence, inversion, fragmentation, phrases in pairs, one climax. |
| `build_project.py` | Melody into REAPER, generate and stage through the server, dress with instruments and effects, save and render. |
| `make_samples.py` | Synthesises the sample library — drums and six melodic instruments — because REAPER ships no instrument beyond ReaSynth and an empty sampler. |
| `upgrade_instruments.py` | Swaps ReaSynth for ReaSamplOmatic5000 loaded with those samples, and builds the drum kits. |
| `analyze_wav.py`, `mix_report.py` | Verification: clipping, discontinuities, crest factor, band balance. |

## Two things measured rather than assumed

**ReaSynDr is not a drum kit.** It answers only to notes where `note % 16 < 4`
(32-35, 48-51, 64-67), so the General MIDI mapping of 36/38/42 produces silence.
All four of its voices are low-frequency with 31-142 ms decays — no hat, no
cymbal. That is why the drums here are sampled instead.

**ReaSamplOmatic5000's pitch map** is linear over -80..+80 semitones on params
5 and 6, and defaults to placing the sample's root at note 69. These samples are
rendered at C (note 60), so the example sets start `-60` and end `+67` to get a
true chromatic map with the root in the right place.

## Caveat on the sound

The samples are synthesised, not recorded. They are a believable instrument, not
a commercial library: an FM electric piano, a Karplus-Strong plucked string, a
detuned saw pad, a reedy lead, and two basses. Point the tracks at real
instrument plugins and the compositions, harmony and arrangements carry over
unchanged — only the instrument on each track differs.
